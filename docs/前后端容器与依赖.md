# 前后端独立容器与部署关系

## 结构

生产Compose包含五个常驻容器与一个一次性迁移任务：

```text
浏览器 / GEO / 客户Agent
          │ HTTPS
总控主机Caddy（公网443，证书持久化由主机负责）
          │ 127.0.0.1:4418
frontend:8080 ── edge网络 ── api:3000
  后台静态资源                 │
                              ├─ PostgreSQL:5432
                              └─ OSS（上传素材、获取归档）
worker ── backend网络 ─────── PostgreSQL / Redis:6379
  │ PostgreSQL Outbox → BullMQ → 构建模板 → OSS归档
  └─ 与API共享platform-data：不可变模板、预览、开发模式对象

客户Agent → 总控同一HTTPS入口 → API领取任务
客户Agent → OSS签名URL或API鉴权下载 → 校验、切换版本
客户Caddy → 客户网站访客
```

frontend只加入edge；api加入edge与backend；worker、数据库、Redis、migrate只加入backend。网络隔离不是外网断网：API和Worker仍需访问OSS。没有给数据库/Redis/API发布主机端口，expose仅描述容器端口，不等于主机端口映射。

## 请求分流与权限

frontend使用Caddy提供public中的页面、CSS、JS和构建时复制的Jodit资源，不运行Node、不挂载业务数据、不读取.env、不持有数据库或OSS凭据。前端构建阶段用锁文件安装依赖，最终镜像不包含node_modules或Node运行时。

以下路径原样代理到API，保留路径和查询参数、Host、Cookie、Authorization及请求体：

- `/api/*`：登录、管理、编辑器图片上传等。
- `/agent/v1/*`：领取任务、心跳、报告、鉴权下载。
- `/webhooks/v1/*`：GEO对接。
- `/preview/*`：登录与网站权限检查仍在API，不能改成公开静态目录。
- `/objects/*`、`/media/*`：本地或旧素材兼容，正式图片建议使用OSS。
- `/health`：API数据库健康检查。

`/frontend-health`仅表示静态前端存活，不代表API、队列、数据库全链路正常。未知静态文件返回404，不用SPA回退掩盖接口错误。静态资源采用no-cache再验证，避免升级后浏览器长期使用旧脚本。

API生产配置为 `SERVE_FRONTEND=false`，且后端镜像不再包含public。保持同源，前端继续使用相对`/api/`，无需增加CORS或在浏览器配置后端地址。外层Caddy应保留原Host（默认行为），不能改成内部api:3000，否则会破坏API的Origin校验。生产保留Secure Cookie，必须通过HTTPS访问。

## 本地验证

```powershell
npm run dev
# 另一个终端：前端容器代理Docker宿主机4418上的本地API
npm run frontend:local
# 打开 http://127.0.0.1:4419
npm run test:frontend
```

若API尚未启动，Windows Docker Desktop验证可在第一个终端先执行 `$env:HOST='0.0.0.0'` 再运行 `npm run dev`。这仅用于开发容器访问宿主API，勿把开发演示账号与该监听方式用于公网生产。

Docker Desktop可使用host.docker.internal；若宿主机API仅监听127.0.0.1导致Docker无法连接，需在启动本地API前设置HOST=0.0.0.0，并限制防火墙访问。Linux也可能需要此设置。该本地Compose不替代生产Compose，不修改现有数据库与Redis。

前端测试使用独立模拟API和临时容器验证所有静态资源、全部代理路径、Cookie/Host/Authorization/Origin、错误状态以及API离线时页面独立存活；业务链路仍使用 `npm test` 的真实PostgreSQL/Redis/Worker/Agent测试。

## 生产与升级

按正式试点文档配置.env与customer-templates，然后：

```text
docker compose -f compose.production.yml up -d --build
```

主机Caddy参考deploy/control.Caddyfile.example，反代目标仍为127.0.0.1:4418，只是这个端口现在属于frontend。客户Agent总控地址、GEO Webhook和后台域名均无需改变。migrate成功后才启动API/Worker；Worker还等待Redis进程启动。frontend等待API进程启动而非业务健康，后端暂不可用时页面可打开、接口返回502。

只更新前端：

```text
docker compose -f compose.production.yml up -d --no-deps --build frontend
```

只更新API或Worker可用同样方式指定api或worker；若包含数据库结构变化，必须先备份、执行migrate并确认兼容，不能绕过迁移。该配置单实例替换会有短暂中断，不是零停机。frontend中断也会暂时影响经过它的API/Agent访问，恢复后Agent继续重试，已发布客户网站不受影响。

数据库、Redis与platform-data仍通过原命名卷持久化。本次拆分不迁移数据库、不清空旧数据；禁止使用down -v作为升级步骤。先在试点环境核对Compose项目名、挂载卷与备份再切生产。

API/Worker仍共享同机platform-data，跨主机扩容需另行解决共享文件；独立前端容器不自动带来多实例或高可用。前端/后端接口更新需兼容相邻版本，重要升级保留旧镜像用于回退。公网TLS、实际OSS与云端网络仍需上线验收。
