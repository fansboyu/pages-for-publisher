# 正式试点版：PostgreSQL 18.6 + 独立构建队列

核对日期：2026-10-16。PostgreSQL 官方版本表的最新稳定版本为 18.6，19 为 RC。本项目固定 `postgres:18.6`，不使用 `latest`、beta 或 RC。API、迁移和 Worker 启动会拒绝低于18.6或标记为预发布的数据库版本。未来补丁升级应先备份、验证再修改镜像标签，不能直接切换数据库大版本。

## 运行结构

```text
运营后台 / GEO API
        ↓
总控 API → PostgreSQL：内容、快照、版本、构建请求、部署任务
                         ↓ 数据库待构建记录（持久化Outbox）
                独立 Worker 的任务调度器
                         ↓
                  Redis / BullMQ
                         ↓
             完整模板 + 冻结内容 → tar.gz
                         ↓
               OSS归档 / 本地归档
                         ↓
            Agent领取部署任务、校验发布包
                         ↓
              Caddy加载新静态版本
```

客户域名直接解析到客户服务器IP，没有服务器池或中间域名调度。Agent仅连接总控HTTPS接口，不开放Redis和PostgreSQL到客户网络。

## 本地启动

要求 Node.js 24、可用Docker、官方Caddy二进制。Windows二进制为 `tools/caddy.exe`；Linux可以通过 `CADDY_BIN` 指向现有Caddy。

```powershell
npm install
npm run dev
```

开发启动器会创建本项目独立的 PostgreSQL 与 Redis 容器及持久卷，随机密码保存在被忽略的 `storage/pilot.env` 中，不输出密码。然后执行数据库迁移，启动API、独立Worker、独立Agent和真实Caddy。

- 正式试点后台：http://127.0.0.1:4418
- Caddy体验网站：http://127.0.0.1:4420/sites/s1/
- 演示管理员：admin / Admin123!
- 代理商：agency / Agency123!；partner / Partner123!
- PostgreSQL本机端口55432；Redis本机端口16379，均仅绑定127.0.0.1。

旧SQLite版仍保留：`npm run dev:legacy`（4318/4320）。两套数据目录与数据库分开。正常使用请打开4418的新试点版。

### 独立进程命令

```text
npm run infra          只启动本项目数据库与Redis
npm run db:migrate     执行显式SQL迁移（需要DATABASE_URL）
npm start              只启动正式API（需要环境变量）
npm run worker         只启动构建Worker（需要环境变量）
npm test               在隔离数据库、端口和队列中验证正式链路
```

直接使用环境文件：`node --env-file=.env pilot/server.mjs` 与 `node --env-file=.env pilot/worker.mjs`。示例为 `.env.pilot.example`。只有显式 `DEMO_MODE=true` 才创建演示账号；生产首次启动必须设置至少14位的 `BOOTSTRAP_ADMIN_PASSWORD`。

## 数据存储

业务分表为 `agencies`、`clients`、`users`、`sessions`、`servers`、`sites`、`templates`、`articles`、`media`、`releases`、`build_jobs`、`deployment_tasks`、`audit_logs`。

`sites.content`只保存该网站的首页字段，`releases.snapshot`保存一次发布的不可变内容快照；它们不是原版把全平台数据保存在一份JSON中的做法。

迁移文件位于 `pilot/migrations/`，由 `schema_migrations`记录。迁移在事务和数据库锁中执行，可重复运行，不使用ORM自动同步结构。生产更新前备份数据库，新增迁移优先采用兼容性的加字段/加表，不能直接修改已应用的迁移文件。

## 构建可靠性与扩容

- API提交发布时，在同一事务中写入发布快照、发布版本、构建请求，再立即返回202和任务ID。
- API不依赖Redis在线；Worker调度器定期读取待构建请求并投递BullMQ，解决数据库写入成功但入队失败的问题。
- 内容快照包括明确的模板版本、站点修订号和文章内容。排队期间继续编辑不会改变已排队版本。
- Worker使用PostgreSQL站点锁，并检查先前任务是否完成。同一网站按发布版本顺序构建，不同网站可以并行。
- 构建失败最多自动尝试3次；超时构建租约可恢复，最终失败可在后台手动重试。
- 增加Worker实例时使用相同数据库、队列名称、Redis及共享数据卷。并发数由 `BUILD_CONCURRENCY` 控制。
- 总控与Worker目前需要共享模板与预览目录；生产Compose已挂载同一个 `platform-data`。跨主机扩容必须提供共享文件存储或进一步把模板/预览改为对象存储读取，不能只在另一台主机启动Worker。

## 完整模板与发布包

后台「服务器与部署」可从服务器允许的目录导入客户模板，再给网站绑定版本。支持既有 `standard-static-v1` 配置、文章卡片、详情页与静态页面。

导入时复制模板，按完整内容计算版本哈希。源文件后续修改不会改变已导入版本，需重新导入。模板应按原规范保留文章占位符；官网内容编辑使用 `{{company_name}}`、`{{home_title}}`、`{{home_description}}`、`{{contact_phone}}`、`{{contact_phone_url}}`。原模板硬编码文字不会自动变为可编辑字段，需要在模板改版时替换为这些占位符。

发布包包含首页、服务、关于、联系、资讯列表、全部已发布文章，以及模板的CSS、JS、字体、固定图片、robots和sitemap。OSS运营图片仅引用URL，不重复进入发布包。

不打包模板源码目录、发布配置、隐藏文件、node_modules、数据库或平台凭据。快照单独归档，不写入客户网站目录。资源与页面校验失败时停止构建，客户旧网站不变。

使用标准 `tar.gz`，内部 `.release-manifest.json`列出网站文件大小与SHA-256。Agent验证包哈希、站点/版本身份、文件哈希和路径，拒绝目录穿越和软链接；清单不被写入网站。

默认限制可配置：

| 配置 | 默认值 |
| --- | --- |
| PACKAGE_MAX_COMPRESSED_MB | 128MB |
| PACKAGE_MAX_UNPACKED_MB | 512MB |
| PACKAGE_MAX_FILES | 20000 |

Agent默认使用同样限制，修改时需同步配置Agent本地限制。Agent 0.3兼容旧JSON包和新tar包；新总控不会向不支持tar包的旧Agent派发新包。

## OSS

继续使用两个私有Bucket：素材、发布归档。`.env.pilot.example`中的OSS配置与阶段一一致。图片上传共用接口，经sharp处理为WebP，返回长期稳定的CDN地址；发布包下载使用短期签名URL。

`STORAGE_DRIVER=local`是本地验证模式，不能代表已验证真实OSS、CDN或公网证书。生产使用OSS时应以客户ECS和真实图片域名完成端到端验收。

## 旧数据迁移

保留原SQLite文件。准备全新的目标PostgreSQL数据库，设置 `DATABASE_URL` 与新的 `DATA_ROOT`，在API首次初始化之前执行：

```text
node scripts/import-legacy.mjs 旧目录/platform.sqlite
```

工具只读SQLite，迁移客户归属、账号密码哈希、站点、文章、素材、版本、操作记录，并复制本地资源。目标库已有用户时拒绝执行，防止覆盖。迁移后旧账号密码仍可使用。

旧版未完成的部署任务不自动重放，保留为cancelled，应核对绑定和Agent地址后重新发布。旧历史包仍可由0.3 Agent读取。旧模板缺少完整源码快照的历史版本仅保留现有产物，不伪造历史模板。

## 生产部署

提供 `compose.production.yml`、`pilot/Dockerfile` 和 `frontend/Dockerfile`：前端、API、Worker、数据库、Redis五个常驻容器，另外有一次性迁移任务。数据库、Redis和API不映射主机端口；前端仅映射主机回环地址4418，前面由总控自己的Caddy提供HTTPS。详见[前后端容器与依赖](前后端容器与依赖.md)。

1. 复制 `.env.pilot.example` 为 `.env`，填写随机密码、总控正式域名、bootstrap密码和OSS配置；数据库与Redis密码建议使用随机十六进制，避免URL转义问题。
2. 创建 `customer-templates`，放入需要导入的客户静态模板。该目录在API容器中只读挂载为 `/imports`。
3. 执行 `docker compose -f compose.production.yml up -d --build`。
4. 总控反向代理指向127.0.0.1:4418。通过HTTPS登录，不要关闭生产Secure Cookie。
5. 注册客户服务器、安装新版Agent、绑定域名与站点，先做单客户试点。

数据库定期使用 `pg_dump`做备份；OSS归档与素材保留策略需覆盖可回滚版本，模板目录也需备份。恢复时先恢复数据库与模板/归档，再恢复API和Worker。不能仅备份Redis。

## 验证与边界

正式测试真实启动PostgreSQL 18.6、Redis、API、两个Worker、Caddy与Agent，覆盖任务补投、构建顺序、内容冻结、完整优佳模板、回滚、停机恢复、富文本、GEO幂等、超32MB/3000文件包与SQLite迁移。报告在 `storage/pilot-tests/<数据库名>/report.json`。

这次没有真实云凭据，因此真实OSS、ECS公网与证书签发/续期未验证。没有添加服务器池或DNS自动切换。会员、任意页面拖拽编辑、自动删除旧资源及跨主机共享存储仍不在本次范围内。
